# Risk Register — Ben Digital Solution

**Version:** 1.9
**Created:** 2026-11-12 (Phase 0)
**Last reviewed:** 2026-11-19 (Phase 7 UI/UX redesign follow-up)
**Owner:** Solo developer / site owner
**Review cadence:** Every phase gate and any time a trigger fires

---

## 1. Method

- **Likelihood (L):** 1 = rare, 2 = unlikely, 3 = possible, 4 = likely, 5 = almost certain.
- **Impact (I):** 1 = negligible, 2 = minor, 3 = moderate, 4 = major, 5 = severe (release blocked, data loss, security breach).
- **Score:** L × I.
- **Rating:** High ≥ 15, Medium 8–14, Low ≤ 7.
- A High risk requires an owner decision before the affected phase can pass its gate. Medium risks need active mitigation. Low risks are monitored.
- Review triggers include: phase gate reached, new dependency advisory, content milestone missed, deployment failure, security finding, or scope change request.

## 3. Top risks in detail

### R-01 — Content shortfall (High)

The platform cannot pass its own success metric without 20 completed chapters. Writing them is the slowest task and competes with engineering time. Mitigation is a fixed cadence, a strict chapter template, and early content milestones tied to phases. If the cadence fails, the owner must explicitly choose a fallback before the release gate; the release cannot be marked complete with fewer chapters unless the success metric and content plan are formally revised.

### R-02 — Solo capacity (High)

One person performs product, engineering, content, QA, and operations. The mitigation is release-scoped phases, lean technology choices, automation in CI, and documentation that allows recovery after a break. No phase is allowed to depend on undocumented local knowledge.

### R-03 — Scope creep (High)

The master prompt explicitly tags features by release. Pulling quizzes, comments, or certificates into R1 would delay the launch and increase risk. Any pull-forward needs a written reason, an ADR, and adjusted acceptance criteria. "While we're here" work is rejected by default.

### R-04 — Next.js security drift (High)

Next.js shipped several security releases in 2026, including critical RCE fixes. R1 pins 16.4.6 and CI audits dependencies. Deployment must never run a version below the latest security floor; upgrading is a planned, tested change with a staging smoke test.

### R-05 — VPS capacity (High)

The stack combines Next.js, Gunicorn, PostgreSQL, and Redis on one low-budget VPS. Memory exhaustion is likely on a 2 GB instance under load. Phase 7 measures real staging usage, sets container limits, and documents the minimum VPS specification. If measurements show a 2 GB instance is insufficient, the owner decides between a larger instance and reducing services; neither is left implicit.

## 4. Accepted risks and conditions

- **PostgreSQL 19 not used:** not GA until 2026-11-19; 18.7 is the supported stable choice.
- **TypeScript 7 not used:** compatibility with Next.js 16 is unverified; 5.9.x is the R1 choice (ADR-0008).
- **No high availability in R1:** a single VPS is accepted for cost; the restore drill and off-host backups are mandatory compensating controls.
- **No second author in R1:** Editor role is usable in `/console` and Django admin but has no assigned second user; solo-author content risk is accepted and tracked as R-01/R-02.
- **Redis is an R1 dependency:** accepted in ADR-0002 with an internal-only, memory-capped instance; sessions use `cached_db` so a cache flush does not log everyone out.
- **No dedicated revision UI in R1:** accepted in ADR-0006; Django admin history plus backups are the recovery path.
- **No CORS in production:** accepted with the single-domain topology (ADR-0009); a future split origin requires a new ADR.
